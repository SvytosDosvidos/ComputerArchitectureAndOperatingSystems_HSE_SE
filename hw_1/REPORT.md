## 1. Формулировка задания (Вариант 22)

### 1.1. Предметный сценарий
На двух морских полях размещены флоты автономных кораблей. В отличие от предыдущего варианта решения о стрельбе принимают сами сохранившиеся корабли. Каждый корабль имеет уникальный номер, положение, размер и количество неповреждённых палуб.

Бой проходит раундами. В начале раунда каждый боеспособный корабль формирует залп. Базовое число выстрелов равно количеству его неповреждённых палуб либо задаётся отдельным правилом. Все цели раунда выбираются до применения повреждений, после чего судья одновременно обрабатывает залпы обеих сторон. Корабль, уничтоженный в текущем раунде, успевает выполнить уже сформированный залп, если не задан иной режим.

Командный центр стороны может согласовывать цели, чтобы уменьшать число повторных выстрелов, но окончательное правило выбора должно быть одинаково доступно обеим сторонам.

Требуется разработать консольное приложение для ОС Linux, моделирующее бой автономных флотов.

### 1.2. Входные параметры
- Размеры морских полей ($W \times H$) и состав флотов (количество 4-, 3-, 2- и 1-палубных кораблей);
- Способ размещения кораблей (автоматический псевдослучайный с соблюдением правил бесконфликтного буфера);
- Правило числа выстрелов в залпе (`alive` — по числу уцелевших палуб, `fixed1` — 1 выстрел, `max2` — не более 2 выстрелов);
- Автономные стратегии кораблей (`random` — случайная разведка, `hunt` — охота на раненых соседей, `checker` — шахматный поиск) и режимы командных центров (`none` — полная автономия, `deconflict` — согласование целей);
- Порядок формирования и одновременного применения залпов судьей;
- Разрешение / запрет повторных выстрелов по уже поражённым клеткам;
- Предельное число раундов;
- Начальное значение генератора псевдослучайных чисел (`seed`) для воспроизводимости;
- Задержка между отображением шагов (`delay_ms`) и файл журнала (`log_file`).

### 1.3. Обязательные наблюдаемые события
- Готовность кораблей (координаты, число палуб, текущая боеспособность и стратегия);
- Сформированные цели каждого автономного корабля на текущий раунд;
- Начало раунда с порядковым номером;
- Применение каждого выстрела (попадание, ранение палубы, промах, уничтожение);
- Изменение боеспособности кораблей (уменьшение числа уцелевших палуб и мощности залпа);
- Уничтожение корабля и его затопление;
- Сводное состояние флотов по завершении каждого раунда и итоговый вердикт Судьи.

### 1.4. Инварианты модели
1. **Инвариант 1:** Уничтоженный до начала раунда корабль не формирует залп.
2. **Инвариант 2:** Число выстрелов строго соответствует состоянию корабля и выбранному правилу.
3. **Инвариант 3:** Все решения раунда принимаются ДО применения повреждений этого раунда.
4. **Инвариант 4:** Корабль, уничтоженный в текущем раунде, успевает выполнить уже сформированный им залп (симметрия одновременности).
5. **Инвариант 5:** Одна палуба не уничтожается повторно.
6. **Инвариант 6:** Обе стороны используют одинаковые правила времени и разрешения конфликтов.

### 1.5. Условия завершения
Бой завершается в следующих случаях:
1. Полное уничтожение всех кораблей Флота А (Победа Флота Б);
2. Полное уничтожение всех кораблей Флота Б (Победа Флота А);
3. Взаимное уничтожение обоих флотов в рамках одного раунда (Ничья);
4. Достижение предельного числа раундов (победа по очкам/уцелевшим палубам либо ничья);
5. Прерывание выполнения пользователем через системный сигнал ОС Linux (`SIGINT`, `SIGTERM`).

## 2. Архитектура программы и отображение сущностей

Программа спроектирована по модульному принципу в соответствии с парадигмой последовательной имитации (discrete-step event simulation) на чистом языке C (стандарт C11). Все сущности предметной области отображены на структуры данных и функции.

### 2.1. Таблица отображения сущностей предметной области

| Сущность предметной области | Структура / Тип в C | Модуль | Описание роли и обязанностей |
| :--- | :--- | :--- | :--- |
| **Автономный корабль** | `struct AutonomousShip` (`ship.h`) | `src/ship.c` | Хранит ID, координаты $(x,y)$, длину, статус каждой палубы `deck_hit[]`, боеспособность `is_alive`, автономную стратегию. Сам формирует цели выстрелов `ship_generate_salvo()`. |
| **Командный центр & Флот** | `struct Fleet` (`fleet.h`) | `src/fleet.c` | Управляет списком кораблей, собственным полем и картой разведки `enemy_revealed[][]`. При включенном `COORD_DECONFLICT` согласует цели кораблей для исключения дубликатов. |
| **Морское поле** | `struct Board` (`board.h`) | `src/board.c` | Двумерная сетка `CellState grid[MAX_DIM][MAX_DIM]`, хранит состояние клеток (чистая вода, целая палуба, подбитая палуба, промах) и карту идентификаторов кораблей. |
| **Судья (Referee)** | `struct Judge` (`judge.h`) | `src/judge.c` | Обеспечивает соблюдение всех инвариантов, арбитраж времени, одновременное применение залпов, подсчет статистики и фиксацию победителя. |
| **Модуль вывода и логов** | `logger.h` | `src/logger.c` | Форматированный вывод в консоль и файл с использованием дескрипторов файлов и системных вызовов (`dprintf`, `open`, `write`, `close`). |
| **Конфигурация модели** | `struct SimulationConfig` (`config.h`) | `src/config.c` | Загрузка настроек через CLI-аргументы и конфигурационные файлы посредством системных вызовов `open()`, `read()`. |

## 3. Выполнение дополнительных требований (на максимальную оценку 8–10 баллов)

### 3.1. Реализация ввода–вывода через системные вызовы и дескрипторы файлов
В соответствии с п. 2 дополнительных требований:
- Вся работа с файлом протокола (`battle_report.log`) организована через получение файлового дескриптора системным вызовом `open()`:
  ```c
  g_log_fd = open(log_filepath, O_WRONLY | O_CREAT | O_TRUNC, 0644);
  ```
- Чтение конфигурационных файлов выполняется системными вызовами `open()` и `read()` с последующим `close()` дескриптора без использования высокоуровневых абстракций `FILE*`:
  ```c
  int fd = open(filepath, O_RDONLY);
  ssize_t bytes_read = read(fd, buffer, sizeof(buffer) - 1);
  close(fd);
  ```
- Весь вывод в терминал и журнал осуществляется системно ориентированной функцией `dprintf()` и `vdprintf()` напрямую в дескрипторы `STDOUT_FILENO`, `STDERR_FILENO` и `g_log_fd`.

### 3.2. Корректное завершение по прерыванию сигналом ОС (SIGINT / SIGTERM)
В соответствии с п. 3 дополнительных требований:
- Установлен обработчик сигналов `sigaction()` для `SIGINT` (Ctrl+C) и `SIGTERM`.
- Обработчик устанавливает атомарный флаг `volatile sig_atomic_t g_interrupted`.
- При получении сигнала симуляция не аварийно падает, а безопасно выходит из цикла раундов, сбрасывает накопленную статистику, выводит отчет в консоль, закрывает файловый дескриптор лога `close(g_log_fd)` и завершается с кодом успешного закрытия `EXIT_SUCCESS`.

### 3.3. Сохранение итогового лога со статистикой
В соответствии с п. 4 дополнительных требований:
- Создается полный журнал боя, куда протоколируются все события в человекочитаемом виде без мусорных escape-последовательностей.
- Фиксируется статистика: общее число раундов, число произведенных выстрелов каждым флотом, попадания, потопленные корабли, причина остановки боя.

### 3.4. Автоматизированные тесты и воспроизводимость генератора
В соответствии с п. 5 дополнительных требований:
- Разработан bash-скрипт `tests/run_tests.sh`, выполняющий 7 автоматических проверок:
  1. Чистая компиляция проекта через `make all` с флагами `-Wall -Wextra -pedantic`;
  2. Проверка интерфейса командной строки и справки `--help`;
  3. Проверка воспроизводимости (запуск с одинаковым `--seed` создает идентичные побайтово логи `cmp -s`);
  4. Запуск с внешним конфигурационным файлом `data/config_small.txt`;
  5. Проверка правил числа выстрелов (`--rule fixed1`, `--rule max2`);
  6. Проверка обработки флага повторных целей `--allow-repeat`;
  7. Тестирование перехвата сигнала `SIGINT` через фоновый `kill -INT`.

## 4. Пользовательский интерфейс и варианты запуска

### 4.1. Формат вызова приложения
```bash
./bin/naval_battle [опции]
```

### 4.2. Доступные параметры
- `-c, --config <file>`: загрузить параметры из конфигурационного файла;
- `-w, --width <int>`: ширина морских полей (от 5 до 30);
- `-h, --height <int>`: высота морских полей (от 5 до 30);
- `-r, --rounds <int>`: предельное количество раундов;
- `-d, --delay <ms>`: временная задержка между раундами в миллисекундах;
- `-s, --seed <uint>`: фиксированное начальное значение ГСЧ;
- `-l, --log <file>`: имя файла журнала;
- `--rule <alive|fixed1|max2>`: правило выстрелов залпа;
- `--coord-a <none|deconflict>`: координация целей флота А;
- `--coord-b <none|deconflict>`: координация целей флота Б;
- `--strat-a <random|hunt|checker>`: стратегия кораблей флота А;
- `--strat-b <random|hunt|checker>`: стратегия кораблей флота Б;
- `--allow-repeat`: разрешение повторных выстрелов;
- `--hide-ships`: туман войны (скрывать непораженные корабли);
- `--no-color`: отключение цветовой ANSI-палитры;
- `--help`: вывод подробной справки.

### 4.3. Примеры сценариев запуска

1. **Базовый наглядный запуск с анимацией:**
   ```bash
   ./bin/naval_battle --delay 300
   ```
2. **Воспроизводимый научный запуск со сравнением стратегий:**
   ```bash
   ./bin/naval_battle --seed 12345 --rounds 50 --delay 0 -l exp1.log
   ```
3. **Запуск из конфигурационного файла:**
   ```bash
   ./bin/naval_battle -c data/config_hunt_vs_random.txt
   ```
4. **Запуск автоматизированных тестов:**
   ```bash
   make test
   ```

### 5.2. Критическая оценка сгенерированного кода и внесенные исправления
В процессе проверки кода были выявлены и исправлены следующие нюансы:
1. **Предупреждение компилятора по флагу `-Wpedantic`:** При передаче двумерного массива `f->enemy_hits` в функцию генерации залпа компилятор GCC выдавал предупреждение `invalid use of pointers to arrays with different qualifiers in ISO C`. Было скорректировано описание типов параметров функции `ship_generate_salvo()`, что обеспечило сборку с 0 предупреждений.
2. **Неявное объявление функции `usleep`:** В стандарте C11 по умолчанию функция `usleep` скрыта заголовком `<unistd.h>`. Добавлен макрос `#define _DEFAULT_SOURCE`, гарантирующий переносимость под стандарты POSIX/Linux.
3. **Строгая одновременность залпов раунда:** Первоначальный драфт мог приводить к ситуации, когда корабль, пораженный первым выстрелом в раунде, терял выстрелы до конца раунда. В итоговом коде четко разделены две фазы: формирование залпов всеми уцелевшими кораблями ДО начала применения урона, и последующее симметричное применение судьей.
4. **Запрет повторного уничтожения одной и той же палубы:** Добавлен явный битовый массив `deck_hit[]` на уровне структуры `AutonomousShip`, исключающий ложные повторные срабатывания при нескольких попаданиях в один сегмент.
